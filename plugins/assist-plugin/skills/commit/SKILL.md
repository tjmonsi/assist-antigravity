# Commit

Usage: `/commit [--squash] [--amend] [--scope SCOPE] [TYPE: message]`

Create conventional commits using the Conventional Commits format.

## Format

```
<type>(<scope>): <subject>

<body>

<footer>
```

**Types:**
- `feat` — A new feature
- `fix` — A bug fix
- `refactor` — Code change without feature/fix
- `docs` — Documentation changes
- `test` — Test changes
- `chore` — Maintenance, dependencies
- `perf` — Performance improvements
- `ci` — CI/CD changes

**Scope (optional):** Component or module affected

**Subject:** Imperative, present tense, no period (50 chars max)

## Examples

```
feat(auth): implement JWT-based authentication

fix(api): resolve null pointer in user endpoint

refactor(database): consolidate query builders

docs(readme): add installation instructions
```

### No Co-Authorship

Commit messages contain no LLM or AI-assistant attribution: no footer, no `Co-Authored-By` line, whatever model the session runs on.

Correct:
```
feat(auth): implement JWT-based authentication

Add JWT middleware and refresh-token rotation for the login flow.
```

Wrong (never do this):
```
feat(auth): implement JWT-based authentication

Add JWT middleware and refresh-token rotation for the login flow.

Co-Authored-By: <AI model name> <noreply@example.com>
```

## Options

- `--squash` — Squash commits before committing (clean history)
- `--amend` — Amend the last commit instead of creating new one
- `--scope SCOPE` — Specify scope for the commit

## Workflow

1. Run `git status --short` with `run_command` and show the result.
2. Stage only what the user names. If the user named no paths, list the candidate files from the status output and confirm the list with `ask_question` before staging. Write the confirmed paths, one per line, to `.agent/tmp/paths-<timestamp>.txt` with `write_to_file`, run `git --literal-pathspecs add --pathspec-from-file=.agent/tmp/paths-<timestamp>.txt` (requires git 2.25 or later; `--literal-pathspecs` stops `*`, `?`, or a leading `:` in a name from matching other files), then delete the file. File names come from the repository and may contain shell metacharacters, so the paths never appear in a shell command line. Never run `git add .`, `git add -A`, or `git add -u`. Exclude `.agent/tmp/` from the list.
3. Never stage a file matching `.env*`, `*.pem`, `*.key`, or `id_*` without the user's explicit confirmation of that specific file.
4. Review `git diff --staged` and choose the commit type and scope.
5. Write the message to a per-run file under the workspace `.agent/tmp/` (for example `.agent/tmp/commit-<timestamp>.txt`) with `write_to_file`. Strip attribution lines from that file (see [Stripping Co-Authorship](#stripping-co-authorship)).
6. Show the message and staged file list, and confirm with the user.
7. Run `git commit -F .agent/tmp/commit-<timestamp>.txt` (add `--amend` for `--amend`). Never build the message with `git commit -m "$(...)"` or any shell string that contains model-generated text.
8. Delete the message file, then verify with `git log -1 --format=%B`.

## Constraints

- Always use Conventional Commits format
- Never commit without review (changes should be reviewed first)
- Keep messages concise and meaningful
- Link to issues/tickets in footer if applicable
- **Commit messages must NOT include co-authorship lines.** No `Co-Authored-By: <model>`, `Generated by <model>`, or any similar LLM attribution (Gemini, Claude, or any other assistant), in the subject, body, or footer.
- Do not set `git config user.name`/`user.email` to an LLM or assistant identity. Commits use the local developer's own git identity (`git config user.name`, `git config user.email`), never an assistant name.

## Model

This skill runs on the main agent, using whatever model the user selected in Antigravity's model selector; skills carry no model setting. Composing a conventional commit message is mechanical (read staged diff, pick a type/scope, write a one-line subject) and needs no deep reasoning, so a fast model such as a Gemini Flash model is enough. ## Stripping Co-Authorship

No helper script exists for this skill (`run_command` running `git` is the only tool it uses). Enforcement is a hard rule for whoever/whatever composes the message:

1. Never generate a `Co-Authored-By`, `Generated-By`, or `Assisted-By` line for any LLM.
2. If the message file contains one of these lines (for example, pasted from another tool), remove it with `replace_file_content` before running `git commit -F`. Then confirm none remain: `grep -n -iE '^(co-authored-by|generated-by|assisted-by):' .agent/tmp/commit-<timestamp>.txt` prints nothing.
3. Verify with `git log -1 --format=%B` after committing; the output must not mention any model or assistant name.

## Report Writing Standard

- Lead with the most important finding; never write "this is the more important of the two."
- Every finding has three parts: what happened, why it matters, what to do next.
- State each conclusion once. One optional summary line at the end for multi-finding reports; never repeat findings there.
- Use active voice, important subject before the verb ("Validation is skipped" not "The validation was skipped by...").
- Cut hedges ("it should be noted," "arguably") and contrastive filler ("This is X, not Y" — state what it is).
- No meta-headers about the act of writing ("What follows," "Key takeaway," "In conclusion").
- No em-dashes; use a period, comma, parentheses, or semicolon.
- No severity badges, remediation blocks, or summary sections unless the reader would be lost without them.
- Never restate the user's prompt or an assumption as fact; report the tested result.
- The first sentence of every paragraph must add new information.
- Applies to commit body prose only; commit subject lines and Conventional Commits type/scope syntax are unaffected.
