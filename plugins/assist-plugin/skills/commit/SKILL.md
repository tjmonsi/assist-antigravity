# Commit

Usage: `/commit [--squash] [--amend] [--scope SCOPE] [TYPE: message]`

Create conventional commits using the Conventional Commits format.

## Format

```
<type>(<scope>): <subject>

<body>

<footer>
```

**Types:**
- `feat`: A new feature
- `fix`: A bug fix
- `refactor`: Code change without feature/fix
- `docs`: Documentation changes
- `test`: Test changes
- `chore`: Maintenance, dependencies
- `perf`: Performance improvements
- `ci`: CI/CD changes

**Scope (optional):** Component or module affected

**Subject:** Imperative, present tense, no period (50 chars max)

## Examples

```
feat(auth): implement JWT-based authentication

fix(api): resolve null pointer in user endpoint

refactor(database): consolidate query builders

docs(readme): add installation instructions
```

### No AI Attribution

Commit messages contain no AI attribution: no AI attribution footer, no `Co-Authored-By` line for an AI tool, no "Generated with" line, no `*-Session:` trailer, and no bare AI session link, whatever model the session runs on. Human co-authors are fine. Nothing checks the message automatically; the rule binds whoever composes it. The full rule is the No AI Attribution Rule in `rules/assist-plugin-rule.md`.

Correct:
```
feat(auth): implement JWT-based authentication

Add JWT middleware and refresh-token rotation for the login flow.
```

Wrong (never do this):
```
feat(auth): implement JWT-based authentication

Add JWT middleware and refresh-token rotation for the login flow.

Co-Authored-By: <AI model name> <noreply@example.com>
```

## Options

- `--squash`: Squash commits before committing (clean history)
- `--amend`: Amend the last commit instead of creating new one
- `--scope SCOPE`: Specify scope for the commit

## Workflow

1. Run `git status --short` with `run_command` and show the result.
2. Stage only what the user names. If the user named no paths, list the candidate files from the status output and confirm the list with `ask_question` before staging. Write the confirmed paths, one per line, to `.agent/tmp/paths-<timestamp>.txt` with `write_to_file`, run `git --literal-pathspecs add --pathspec-from-file=.agent/tmp/paths-<timestamp>.txt` (requires git 2.25 or later; `--literal-pathspecs` stops `*`, `?`, or a leading `:` in a name from matching other files), then delete the file. File names come from the repository and may contain shell metacharacters, so the paths never appear in a shell command line. Never run `git add .`, `git add -A`, or `git add -u`. Exclude `.agent/tmp/` from the list.
3. Never stage a file matching `.env*`, `*.pem`, `*.key`, or `id_*` without the user's explicit confirmation of that specific file.
4. Review `git diff --staged` and choose the commit type and scope.
5. Write the message to a per-run file under the workspace `.agent/tmp/` (for example `.agent/tmp/commit-<timestamp>.txt`) with `write_to_file`. Strip attribution lines from that file (see [Removing AI Attribution](#removing-ai-attribution)).
6. Show the message and staged file list, and confirm with the user.
7. Run `git commit -F .agent/tmp/commit-<timestamp>.txt` (add `--amend` for `--amend`). Never build the message with `git commit -m "$(...)"` or any shell string that contains model-generated text.
8. Delete the message file, then verify with `git log -1 --format=%B`.

## Constraints

- Always use Conventional Commits format
- Never commit without review (changes should be reviewed first)
- Keep messages concise and meaningful
- The Report Writing Standard below applies to the commit body only; the subject line and the Conventional Commits type and scope syntax follow the Format section
- Link to issues/tickets in footer if applicable
- **Commit messages must NOT include AI attribution lines.** No `Co-Authored-By: <model>`, `Generated by <model>`, or any similar LLM attribution (Gemini, Claude, or any other assistant), in the subject, body, or footer. Human co-authors and issue links are fine. A project's own disclosure or trailer rule takes precedence.
- Do not set `git config user.name`/`user.email` to an LLM or assistant identity. Commits use the local developer's own git identity (`git config user.name`, `git config user.email`), never an assistant name.

## Model

This skill runs on the main agent, using whatever model the user selected in Antigravity's model selector; skills carry no model setting. Composing a conventional commit message is mechanical (read staged diff, pick a type/scope, write a one-line subject) and needs no deep reasoning, so a fast model such as a Gemini Flash model is enough. See [../do/references/model-routing.md](../do/references/model-routing.md) for the full routing table.

## Removing AI Attribution

No helper script exists for this skill (`run_command` running `git` is the only tool it uses). Enforcement is a hard rule for whoever/whatever composes the message:

1. Never generate a `Co-Authored-By`, `Generated-By`, or `Assisted-By` line for any LLM, a `*-Session:` trailer, or a bare AI session link.
2. If the message file contains one of these lines (for example, pasted from another tool), remove it with `replace_file_content` before running `git commit -F`. Then run `grep -n -iE '^[[:space:]]*(co-authored-by|generated-by|assisted-by|[a-z][a-z0-9-]*-session)[[:space:]]*:|generated[[:space:]]+(with|by)([^[:alnum:]]|$)' .agent/tmp/commit-<timestamp>.txt` and read every line it prints, and look for any bare AI session link. The footer branch is unanchored so that a footer after an emoji still matches; the command can also print human co-author lines and body sentences that use the phrase, so judge each printed line.
3. Verify with `git log -1 --format=%B` after committing; the output must hold no AI attribution line. If one is there, remove only that line from a new message file, show the amended message in chat, and confirm with `ask_question` before running `git commit --amend -F <file>`. Amend before pushing, and only after the user confirms.
4. If a line you would remove names a person the user asked to credit, stop and ask the user instead of removing it.

## Report Writing Standard

- Put the answer or the most important finding first. No preamble, no restating the question, no closing recap.
- Let content set the length. Report a clean check in one line.
- Give each finding three parts: what happened, why it matters, what to do next.
- State each conclusion once. Open every paragraph with new information.
- Use active voice; put the important subject before the verb.
- Use plain words ("use" for "utilize"). Cut hedges, intensifiers, throat-clearing, buzzwords, and "not X but Y" framing; state what it is.
- Name headings after their content. Skip summary labels ("In conclusion", "Key takeaways"), severity badges, and summary sections unless the reader needs them.
- Write no em dashes (use a period, comma, colon, parentheses, or semicolon), no curly quotes, and no chatbot sign-offs or offers.
- Back every claim with evidence (file and line, log, test result, URL) and every number with a source; label estimates as estimates.
- Report tested results; never present the prompt or an assumption as fact.
- Quote exactly; never reword a quotation.
- Keep ticket ids and internal blame out of user-facing text.
